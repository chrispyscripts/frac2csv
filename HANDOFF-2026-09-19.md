## 1. Liberty's red comb (#682-#687, #677) — FIXED in v1.11.8

**It was never stage 1 only, and that premise cost time.** All seven reports
name stage 1 because stage 1 is the one you open first. Measured on 00949,
Treating Pressure, share of samples jumping more than a quarter of the range:

```
stage 1   56.7% -> 0.0     median step 28.592 -> 0.022 MPa
stage 2   83.5% -> 0.0                16.045 -> 0.016      <- the worst one
stage 3   37.9% -> 0.0                10.790 -> 0.017
stage 4   44.9% -> 0.0                10.576 -> 0.021
```

**The cause.** Every Liberty stage page prints TWO plots: the Treatment Plot
on top and a Chemicals Plot under it. Both draw a curve in pure red — Treating
Pressure above, **J475 Conc** below — and `lib1` groups a page's series by
COLOUR across every drawing on the page. 00949 p97 has **36 red paths where
every other colour has exactly 18**, and red is the only colour appearing in
both frames. J475 never even reached `named`: red was already taken by
Treating Pressure and the lookup is a `setdefault`, so its ink simply went
into the pressure. Sitting below the pressure frame it clips to the bottom of
that axis — hence a series alternating between a real pressure and ~0 once per
x-slice, with the ghost smooth across the top.

**The fix.** `lib1._value_panels` finds the frames from the value gridlines
(they run the full time width of their own plot and nothing else: ~20 units
apart inside a frame, ~140 across the gap, and the threshold is taken off the
page's own spacing). Each series is then bounded to the plot its own legend
entry sits in. A single-plot page returns no panels and nothing is filtered,
which is every other template we read. `tests/test_lib1_panels.py`, 9 checks.

All six reported files come back 0.0% on every channel except GORV, which is a
flat channel with a 0.2 MPa range where "a quarter of the range" is pen
jitter — unchanged by this and not a comb.

**Still open on that file**, and unrelated: a banner reading "2 stages start
before the stage before them finished — 16, 20". Clock trouble.

**#677** was closed as not-a-defect on axis-tick evidence and that reasoning
still stands.

## 2. Trican "truncation" (#665, #668, #669, #679, #680, #681) — fixed in v1.11.6

**Nothing is being lost.** On `00218`: 27 of 29 stages trimmed, every one by
exactly **11.0 min**, and **all 27 cuts genuinely covered** by the next chart.
That uniform 11 min is the Trican report format re-plotting the previous stage,
so the handover fires on nearly every stage of every file of that type — which
is why he says "all Trican-2".

Index by IDENTITY, not by stage label, when checking coverage. Labels repeat
(see §4) and keying a dict by them silently compares the wrong charts. That
mistake produced a confident, wrong "22 minutes lost" report earlier today.

**Naming trap:** "Trican-2" is Carmine's own code for `trican2.py`, a TABLE
parser ("Trican-2 in Carmine's codes" — its own docstring). His chart pages go
through **`trican_charts.detect`, which is layout A**. On 00218: 29 layout-A
pages, 28 `trican2` table pages, **0 layout-B pages**. The layout-B deduction
work shipped in v1.11.1 is real but touches none of his Trican-2 reports.

**Status: found and fixed in v1.11.6. He was right the whole time.**

The tail was read, trimmed, shipped and drawn correctly, and then thrown away
on the last step before the chart. `stageItems()` in `lab/public/index.html`
builds the objects the stage list opens and names every field it keeps —
`handover` was not among them. So it drew when a stage was handed straight to
`setGraph`, which is how v1.11.3, v1.11.4 and v1.11.5 were each verified, and
never on the only path a user has: drop, Extract, click a stage.

Walking all 29 stages of `00218` through the real UI: `tail 0, band false,
painted 0` on every one. With the field carried through: 27 of 29 draw the
band, stage 1's axis reads 107 min against the page's 195-302 elapsed, and the
shutdown inside the band is visible (60.3 -> 27.4 MPa, 8.4 -> 2.0).

**The lesson, and it cost three releases:** each of those was verified by
feeding a stage object straight to the drawing code. That path is not the
product. Verify through the UI the user actually drives -- drop the file, click
the stage -- or you are testing a function, not a feature.
`tests/test_stage_handover.js` now holds the line: remove the one field from
`stageItems` and it fails.

Nothing was ever wrong with the trim itself, and nothing changed in the CSV.

## 3. The spikes (#653, #656, #658, #660, #661, #662) — diagnosed, no automatic fix

**Measured on 00028 p97: 3,860 samples, not one sits off the ink by more than
2 px.** The tracer is not inventing rows. It is following the WRONG ink — a
second run of the same colour in the column (a gridline, a neighbour's
anti-aliased fringe, a legend swatch). Both candidates are genuinely there and
no rule separates them across templates; three attempts at automatic
gap-filling have already been backed out of this project.

**A/B on his chart 41, old tracer vs new: 135 spikes before, 135 after.** The
v1.11.3 envelope fix is a real bug fix — no column may report outside its own
ink — but it does **not** address his spikes. An earlier claim that it covered
eight reports was wrong.

**Fix in box** (v1.11.3, persisted v1.11.3) is the manual answer: drag a box,
the curve inside is re-read off the page, pen colour sampled from the trace
just OUTSIDE the box so a crossing curve is not picked up. Corrections are
keyed `file::stage::channel` and re-applied on every read.

## 5. "No extractable data" — THREE causes, not one (#666, #675, #678)

The handoff before this one called these "14 files, one cause". They are not.
Read the issues for the actual file names; the guesses about which file is
which were wrong twice.

**a. Daily reports, not charts — answered in v1.11.9.** `00426`, `00428`,
`00429` are 124-page runs of Petrosight *Daily Initial Completions Report*
sheets. Well shut in, no treatment chart anywhere in them. Every page is a
single 2200x1700 scan, no text layer, no vectors. The reader used to answer
with two guesses at once; it now OCRs the banner (tesseract IS bundled in the
Windows build) and says what the document is. Nothing to fix in the reader —
these files have no charts.

**b. Pages skipped as schematics** — `00853`, `00858` (#675): "5-6 page(s)
skipped as schematics or tables that draw like charts (p4..p8)" and then
nothing found in 232 / 288 pages. Unexamined. Start by rendering p4-p8 and
deciding whether the skip is right.

**c. Unreadable chart fonts** — `00065-200C037K094H0300_30533` and
`00066-200B072F094H0300_30534` (#666), 92 and 91 pages. This IS the
subset-font case: text comes back as glyph indices, and no single-byte shift
from -80 to +80 decodes it. `ocr_labels` exists for exactly this; the fix is
detection-side, since the routing decision is itself made on text.

**Also in #678 and unrelated to any of the above:** `00427` reports
"surface chart — step1: no frame — on 22 page(s)". A frame-detection failure,
not a routing one.

**Trap:** `00065` and `00066` name a DIFFERENT file in five different corpus
folders. The AER-Frac-Duvernay `00065` reads perfectly (12 BJ stages). Match
on the full name from the issue, never the leading number.

  has no reader `.py` on disk, so the cache key never changed between versions.
  Carmine had been served pre-v1.10.0 results for every file he had already

## 7. Gotchas worth keeping

- **`x or ()` on a numpy array raises.** Test against None. Cost a release
  once and nearly a second time the same day.
- **Index charts by identity, never by stage label.** Labels repeat.
- **"Trican-2" is a table parser.** His chart files are layout A.
- **`lib1` and `halliburton_ifs` are vector readers** — `auto_raster` changes
  cannot affect them.
- **`lab/api/` is a stale mirror** — `auto_raster.py` there is 1,015 lines
  against 1,412 and has no envelope step at all. It is the deployment surface
  for the web Lab. Carmine is on desktop so it does not reach him.
- **The EXE is unsigned.** Defender flags every release. `--onefile` +
  unsigned + zero reputation. The certificate is the only real fix; the free
  interim is submitting each build to Microsoft as a false positive.
- **`LOG_KEEP = 5`** counts files, not launches. Launch portals in batches and
  you keep about one batch of history.
- Drives drop off the bus regularly. `find_drive_roots()` caches roots per
  process — restart portals after remounting.
