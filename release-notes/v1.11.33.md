**FracView: "adjust" no longer pulls data backwards or cuts a stage off after a date change.** A FracView edit is a set of absolute cut points on the clock, saved per file, and applying it means comparing those points against where the stages sit now. That is exact as long as the stages have not moved — and a date correction moves them. On 00100, giving interval 19 its real year shifted that stage by sixteen years, so every saved boundary addressed a timeline that no longer existed: the stage fell outside every bound and contributed nothing, which is the "cuts off", while its neighbours were cut at points meant for somewhere else, which is the "pulls data backwards". Both halves of the report, from one cause.

**An edit now remembers the timeline it was drawn on, and is refused against any other.** The boundaries are the most expensive thing in this app to recreate — all of it done by eye — so they are dropped only when they provably no longer mean what they meant. A refused edit is set aside rather than applied, which leaves the well as read instead of cut at the wrong places: the better of the two failures. Correct the dates first, then draw the boundaries, and they hold.

**Edits saved before this release carry no timeline.** Rather than throw them away or trust them blindly, each is accepted once if its span still lies inside the well's own — an edit drawn on the current layout always does, and one drawn on a layout sixteen years away cannot — and is stamped on the way through, so the question is asked once and never again.

**Which templates this release touches:** the Lab only (FracView). No reader changed, so every filing reads exactly as it did under v1.11.32.
